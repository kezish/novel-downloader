# 搜索：关键词、意图、排序与缓存

`novel-cli search`、`POST /api/v1/search`、桌面客户端搜索框与 Android 搜索调用的是同一套聚合实现（`plugins.search` / `plugins.ranking`）。本页说明关键词如何被理解、结果为什么这样排序、过滤与缓存如何生效，以及失败时命令的退出码和 JSON 行为。

流式搜索（`GET /api/v1/search/stream` 与桌面/Android 的渐进式结果）只复用其中的「按站点取数 + 清洗 + 本地过滤」，不排序、不判定意图，也不附加派生字段；差异见 [本地 API 服务](./api.md) 的流式章节。

## 一次搜索的处理顺序 {#pipeline}

1. 解析参数与站点选择。显式写了不存在的 `--site` 时，CLI 在发请求前就以用法错误退出（`2`），不会退化成「0 条结果」。
2. 规范化关键词，组装缓存 key 并查缓存（见 [缓存](#cache)）。
3. 缓存未命中时，并发请求所选站点：每个站点一个 `per_site_limit` 与一个 `timeout` 墙钟预算，整体耗时约等于 `timeout`，而不是被最慢的站点拖住。
4. 清洗每行：丢弃站点 key 不可用、或既没有可用 `book_id` 又没有可用 `book_url` 的行；清掉非 `http(s)` 的链接，去掉标题、作者等展示字段里的控制字符与 ANSI 序列。
5. 同一站点内折叠精确重复行（跨站点的同名书只在 `--group` 时才合并）。
6. 判定查询意图（仅 `sort=quality`，见 [查询意图](#query-intent)）。
7. 排序（见 [排序](#ranking)）。
8. 应用本地过滤：字数上下界、更新时间下界（见 [过滤](#filters)）。
9. 仅 `sort=quality` 时应用相关度下限（见 [排序](#ranking)）；它只会保留更相关的结果，但**永远不会把结果清空**。
10. 可选跨站合并（`--group`），每本书一行，`sources` 按最佳来源排序。
11. 应用 `limit`（`--group` 时按「本」计数，否则按行计数）。
12. 为每个最终行附加只读派生字段 `rank_score`、`match_tier`、`query_intent`。

缓存保存的是**未排序的合并快照**，所以排序、分组、`limit` 的每次调用都在自己的副本上完成，不会互相污染，也不会写回缓存。

## 关键词规范化 {#normalization}

关键词在参与匹配、去重、分组和缓存之前，会被 `ranking.normalize_text` 规范化：

| 步骤 | 作用 | 例子 |
| --- | --- | --- |
| NFKC | 全角折成半角、兼容字符折叠、组合字符规范化 | `ＡＢＣ` → `ABC`；`１２３４` → `1234` |
| casefold | 大小写不敏感 | `ABC` → `abc`；`Straße` → `strasse` |
| 删除 `[\W_]+` | 去掉标点、空白、符号、下划线，保留各语言的字母与数字 | `Re:Zero` → `rezero`；`斗破 苍穹` → `斗破苍穹` |

由此可知：

- `"斗破 苍穹"` 与 `"斗破苍穹"` 是同一个查询，共享缓存条目；
- `"ＡＢＣ"` 与 `"abc"` 视为同一标题/作者；
- 关键词首尾空白、句读、书名号（`《》`）、英文冒号等都不会影响命中；
- 只由标点组成的查询（如 `"!!!"`）规范化后为空：**匹配**时视为空关键词，但**缓存 key** 会回退到 NFKC 后的原文，因此 `"!!!"` 与 `"???"` 不会错误地共用一份快照。

同一套规范化也用于结果去重与分组：两行的书名只有全角/半角或标点差异时，会被当成同一个书名。

## 多词查询（书名 + 作者） {#multi-word}

聚合搜索允许把「书名」和「作者」写在同一个关键词里。关键词先做 NFKC，再按以下字符切分：

- 任意空白（含全角空格 `U+3000`）
- 间隔号 `·`
- 半角逗号 `,` 与全角逗号 `，`
- 半角连字符 `-`（全角 `－` 经 NFKC 后同样会被切分）

切分后，只有 **2–4 个互不相同的非空词** 才启用多词评分。其余情况保持原行为：

| 词数 | 行为 |
| --- | --- |
| 1 | 普通查询，整串关键词与标题/作者比较 |
| 2–4 | 每个词分别与标题、作者比较；取「最佳标题词 + 最佳作者词」参与相关度 |
| 5 或更多 | 视为粘贴进来的整句，仍按单串关键词处理 |

整串关键词始终保留在比较中，因此多词评分只会**提高**相关度，不会把原本能命中的标题压低。多词查询同样用于 `match_tier` 和查询意图判定。

```bash
# 两种写法等价（推荐加引号，避免 shell 自行拆分）
novel-cli search "斗破苍穹 天蚕土豆"
novel-cli search 斗破苍穹 天蚕土豆

# 间隔号、逗号同样是分隔符
novel-cli search "斗破苍穹·天蚕土豆"
novel-cli search "斗破苍穹，天蚕土豆"
```

!!! note "多词拆分不改变缓存 key"
    缓存身份是**规范化后的完整关键词**，不是切分后的词表。因此 `"斗破苍穹 天蚕土豆"` 与 `"斗破苍穹"` 是两个不同的查询，各自缓存；而 `"斗破 苍穹"` 与 `"斗破苍穹"` 是同一个查询。多词拆分只影响排序评分与意图判定。

## 查询意图 `query_intent` {#query-intent}

短关键词既可能是书名也可能是作者名。`quality` 排序会先对**整批结果**做一次判定：这批结果整体更像「按书名找」还是「按作者找」，然后把判定结果反馈给排序。

判定方法（`ranking.detect_query_intent`）：

1. 对每一行，分别计算关键词与 `title`、`author` 的相似度，并累加（用 `math.fsum`，与行的到达顺序无关）。
2. 按规范化后的关键词长度给两侧加权：

   | 关键词长度 | 书名权重 | 作者权重 | 理由 |
   | --- | --- | --- | --- |
   | ≤ 4 字 | 0.35 | 0.65 | 中文笔名多为 2–4 字 |
   | 5–9 字 | 0.50 | 0.50 | 两种解释都合理，让实际匹配决定 |
   | ≥ 10 字 | 0.65 | 0.35 | 这个长度几乎都是完整书名 |

3. 两侧加权分相差不超过总分的 **15%**（或完全没有重合）时，判定为「无明确意图」；否则取分数更高的一侧。

多词关键词按词逐个判定：所有有证据的词都指向同一侧时才采用该判定；一个词指书名、另一个指作者（典型的「书名 + 作者」查询），或证据不足，都返回「无明确意图」。

判定结果的去向：

- 只有 `sort=quality` 会计算并使用它；显式使用 `--sort priority/site/title/author/words/update` 时不计算，`query_intent` 输出为 `null`。
- 判定基于**清洗、去重之后、过滤/分组/截断之前**的整批结果，因此过滤条件不会改变判定。
- 它不影响哪些行被保留（除非通过下述排序与相关度下限间接影响），也不写回缓存。

### 它如何影响排序

一旦判定为 `title` 或 `author`，`quality` 排序使用两级键：

```text
(主字段的 match_tier, rank_score)
```

也就是说：**主字段上匹配得更「像」的行永远排在前面**，即使对方字数更多、更新更近、封面章节更齐全。这样，一次作者搜索里，作者本人那本「元数据稀疏」的书不会输给一本「书名恰好包含作者名」的富元数据书。判定为「无明确意图」时退回单级 `rank_score` 排序（历史行为）。

### 在哪些界面显示

| 界面 | 展示位置 |
| --- | --- |
| CLI | 结果页标题，例如 `搜索结果 · 第 1/2 页 · 书名匹配` 或 `· 作者匹配` |
| 桌面客户端 | 结果数量旁的**列表级**标签（`书名匹配` / `作者匹配`） |
| Android | 结果数量旁的列表级标签，仅当结果非空且判定为 `title` / `author` 时出现 |
| JSON | `POST /search` 的每一行带 `query_intent`，响应顶层也有同名字段（`"title"` / `"author"` / `null`） |

`query_intent` 是**查询级**判定；行级判定是 `match_tier`，两者不是一回事：一行可以匹配得很好，而整次查询仍没有明确意图。流式端点、榜单浏览与旧缓存快照没有这些派生字段。

## 排序 {#ranking}

### `rank_score`：0..1 的质量分

`ranking.rank_score` 把五个信号加权求和（权重合计 1.0）：

| 信号 | 权重 | 计算方式 |
| --- | --- | --- |
| 关键词相关度 | 0.55 | 见下方匹配细则；判定出意图时主字段被放大 |
| 字数 | 0.15 | `log10(字数) / 7`，上限 1.0；无法解析时取 0.5 |
| 更新新鲜度 | 0.12 | ≤1 天 1.0；≤7 天 0.98；≤30 天 0.95；≤90 天 0.9；≤365 天 0.8；≤730 天 0.6；更早 0.5；无法解析时 0.5 |
| 站点优先级 | 0.08 | `priority` ≤10 → 1.0；≤50 → 0.9；≤100 → 0.75；≤200 → 0.6；≤500 → 0.45；≤1000 → 0.3；更大 → 0.2；缺失/`NaN` → 0.6 |
| 完整度 | 0.10 | 有封面 +0.5，有最新章节 +0.5 |

相关度本身按字段分别计算（整串关键词与每个词都参与，取较高值）：

| 匹配关系 | 标题得分 | 作者得分 |
| --- | --- | --- |
| 完全相等 | 1.00 | 0.90 |
| 前缀 | 0.75 | 0.70 |
| 包含 | 0.70 | 0.70 |
| 只有部分字符重合 | 0.55 × 覆盖率 | 0.50 × 覆盖率 |
| 完全不重合 | 0 | 0 |

再按意图合并两侧：`either` 取 `max(标题, 作者 × 0.9)`；判定为 `title` 取 `max(标题, 作者 × 0.6)`；判定为 `author` 取 `max(作者, 标题 × 0.6)`。

输出中的 `rank_score` 保留 6 位小数。它含更新新鲜度信号，所以同一查询在不同时间调用时可能有极小漂移；`match_tier` 与 `query_intent` 对同一关键词和结果集是确定的。

### `match_tier`：4..0 的匹配层级

| 值 | 含义 |
| --- | --- |
| `4` | 规范化后与字段完全相等 |
| `3` | 字段以关键词开头（前缀） |
| `2` | 关键词出现在字段内部（包含） |
| `1` | 只有关键词的部分字符出现在字段中 |
| `0` | 没有任何字符重合 |

判定出意图时，报告意图主字段的层级；否则报告书名/作者中更好的那个。多词查询报告任一 token 达到的最好层级。`quality` 排序下，这个层级就是排序的外层键。

### 排序键与自然方向

| `--sort` | 比较内容 | 自然方向 |
| --- | --- | --- |
| `quality`（默认） | 判定出意图时 `(match_tier, rank_score)`，否则 `rank_score` | `desc` |
| `priority` | 站点数字优先级；数字**越小越优先**，缺失或 `NaN` 按 0 | `asc` |
| `site` | 规范化后的站点 key | `asc` |
| `title` | 规范化后的书名 | `asc` |
| `author` | 规范化后的作者 | `asc` |
| `words` | 解析后的字数；无法解析按 -1 | `desc` |
| `update` | 解析后的更新时间戳；无法解析按 -1 | `desc` |

`--order asc|desc` 覆盖自然方向。几个常见组合：

```bash
# 最近更新的在前（update 的自然方向就是 desc）
novel-cli search 三体 --sort update

# 字数最少的在前（words 自然方向是 desc，需显式 asc）
novel-cli search 三体 --sort words --order asc

# 站点优先级高的在前（priority 自然方向是 asc，因为数字小 = 更优先）
novel-cli search 斗破苍穹 --sort priority

# 按书名升序，并以 JSON 输出
novel-cli search 三体 --sort title --json
```

`words` / `update` 无法解析时按 -1 参与比较：在默认降序下排最后，在 `--order asc` 下排最前。`title` / `author` / `site` 的空值按空串参与升序，因此会排在最前。

### 相关度下限（仅 `quality`）

`quality` 排序还会应用一个默认 **0.45** 的相关度下限（未暴露为 CLI/API 参数）：

- 不分组时逐行判断，分组时判断每本书的**主行**（镜像站点的另一条记录单独看可能不相关，但书本身是相关的）；
- 阈值取的是 `relevance_of`（纯关键词相关度，不含字数/时间/优先级），不是 `rank_score`；
- 它**永远不会把结果清空**：若没有任何行达到阈值，就保留所有相关度大于 0 的行；若连这些也没有，输入原样返回。
- 显式使用 `--sort words` / `update` 等键时**不应用**，因此切换排序不会因为相关度丢行。

### 平局如何打破 {#tie-break}

排序是两次稳定排序：

1. 先按行的**内容元组**做一次全序预排序：`(site, 规范化书名, book_id, 规范化作者, book_url, word_count, update_date, latest_chapter, cover_url, priority)`；
2. 再按主键（与方向）稳定排序。

因此主键相同的行不会退回到「谁先返回谁在前」——并发搜索时站点完成顺序不同，最终顺序仍然一致。派生字段 `rank_score` / `match_tier` **不参与**比较，旧缓存里残留的标注也不会影响排序。

## 过滤 {#filters}

过滤是**本地**步骤：站点照常返回结果，服务端只保留满足条件的行。它发生在排序之后、`--group` 合并与 `limit` 截断之前，因此被过滤掉的行不会占用「一本书」或一个 `limit` 名额。

### 字数：`--min-words` / `--max-words`

- 上下界都**含边界**，取值 `0`–`1000000000`（CLI、REST 同一上限）。
- 解析规则与排序层一致：`"30万字"` → 300000、`"1,234"` → 1234、`"1.2M"` → 1200000、`"3千字"` → 3000；全角数字与分隔符先经 NFKC。
- 只要设置了任一八字数过滤，**没有字数或无法解析**的行就会被丢弃——即使 `--min-words 0` 也一样，因为过滤处于启用状态。

### 更新日期：`--updated-after`

- 接受 `YYYY-MM-DD`（CLI 严格匹配该格式；REST 由 schema 解析），表示**含当天**的下界：当天任何时刻更新的行都通过。
- 相对日期（行里 `update_date` 形如 `"3天前"`）按**本次调用统一的一个时钟**换算，因此同一次搜索里所有行使用同一基准。
- 设置后，**没有更新日期或无法解析**的行会被丢弃。

### 边界情况

| 情况 | 结果 |
| --- | --- |
| `--updated-after` 是未来日期 | 没有行能满足下界，返回空结果；这不是错误（站点正常作答时退出码仍为 `0`） |
| `--min-words` 大于 `--max-words` | CLI 与桌面端在发请求前按用法错误拒绝（CLI 退出码 `2`）；REST schema 只校验各自的 `0..1000000000` 范围，不做跨字段比较，因此会返回 `200` 与 `total: 0` |
| 日期不是 `YYYY-MM-DD` | CLI 退出码 `2`，不会退化成「无过滤」；REST 返回 `422` |
| 字数超出范围或不是整数 | CLI 退出码 `2`；REST 返回 `422` |
| 过滤后所有行都被丢弃 | 返回空结果，退出码 `0`（是「没有符合条件的结果」，不是请求失败） |

过滤条件只缩小本次结果集，不改变排序评分、响应字段或缓存中的原始快照。不同的过滤组合是不同的请求，会分别缓存，不会复用未过滤的快照。

```bash
# 30 万字以上、100 万字以下，且 2024-01-01 当天或之后更新
novel-cli search 斗破苍穹 --min-words 300000 --max-words 1000000 --updated-after 2024-01-01

# 过滤 + 跨站合并 + 单行 JSON
novel-cli search 斗破苍穹 --min-words 300000 --updated-after 2024-01-01 --group --json
```

REST 的等价请求：

```bash
curl -s -X POST "$BASE/api/v1/search" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"keyword":"斗破苍穹","sites":["qidian","biquge5"],"per_site_limit":10,"min_words":300000,"max_words":1000000,"updated_after":"2024-01-01"}'
```

过滤后结果变少，通常是站点没有返回 `word_count` / `update_date`，而不是搜索失败；排查步骤见 [故障排查](./troubleshooting.md) 的「搜索过滤后没有结果」。

## 缓存 {#cache}

搜索缓存保存的是**合并后、未排序的原始快照**：命中后不再访问任何站点，但每次调用仍按自己的 `sort` / `order` / `limit` / `group` 重新排序、分组与截断。

### 缓存 key 由什么组成

| 组成 | 是否参与 | 说明 |
| --- | --- | --- |
| `keyword` | 是 | 规范化后的完整关键词；纯标点查询回退到 NFKC 原文 |
| `sites` | 是 | 每个 key 去空白、转小写、数字开头补 `n`，再去重排序；`None`（全部站点）与空选择不同 |
| `per_site_limit` | 是 | 每站抓取条数不同 → 快照不同 |
| `nsfw` | 是 | 是否包含 NSFW 搜索器 |
| `timeout` | 是 | 墙钟预算不同可能丢掉不同的慢站点 |
| 配置指纹 | 仅聚合 | `sites` 为 `None` 时附加：参与站点集合 + 浏览器辅助站点集合的 SHA-256 前缀（16 个十六进制字符） |
| `min_words` / `max_words` / `updated_after` | 是 | 过滤条件改变「接受哪些行」；日期统一成 ISO 形式 |
| `sort` / `order` / `limit` / `group` / 相关度下限 | **否** | 纯展示/选择参数，在缓存快照之上按调用重新应用 |

几个直接推论：

- 改了 `--sort`、`--limit` 或 `--group` 仍然命中同一份快照；
- 改了 `--site`、`--site-limit`、`--timeout`、过滤条件，或换了一个关键词，就是另一条缓存；
- 聚合搜索（不写 `--site`）在站点集合或浏览器辅助配置变化后指纹改变，旧条目全部失效，第一次会全部未命中；
- 整次搜索一条结果都没有时**不会**被缓存（多半是临时故障），以免把一次失败固定整个 TTL。

### 内存层

- 进程内、默认启用；TTL **300 秒**，容量**64 条**，超出时按 LRU 淘汰。
- 只存在于当前进程：每次运行 `novel-cli` 都是新进程，所以普通 CLI 调用之间通常不会互相命中；长驻的桌面端或本地 API 进程才会复用。

### 磁盘层（可选）

磁盘层用于跨进程复用，需要在**搜索模块首次导入之前**设置环境变量（对 CLI 即启动该进程之前）：

```bash
# Git Bash / Linux / macOS
NOVELDL_SEARCH_CACHE_DIR=~/.cache/novel-downloader/search novel-cli search 三体
```

```powershell
# PowerShell
$env:NOVELDL_SEARCH_CACHE_DIR = "$env:LOCALAPPDATA\novel_downloader\search-cache"
novel-cli search 三体
```

磁盘层与内存层使用同一 TTL、同一 key、同一字段白名单：

- 目录路径支持 `~` 展开；不设置变量时完全不写文件；
- 文件名为 `v1-<sha256>.json`，payload 内含版本号与完整 key，key 不匹配或版本不同一律视为未命中；
- 每个文件上限 2 MiB，目录内最多保留 256 个本格式文件，超出按修改时间清理最旧的；
- 写入是「同目录临时文件 + `os.replace`」的原子替换，POSIX 下权限为 `0600`；
- 缺失、不可读或损坏的文件只是未命中，下一次写入会重建；
- 磁盘命中会提升到内存，并继承剩余的 TTL，不会变相延长寿命。

### 清理

- **桌面端**：「设置 → 搜索缓存」提供「清除搜索缓存」，同时清空内存与磁盘条目；累计的命中/未命中计数保留。
- **仅内存模式**：重启进程即可。
- **手动清理磁盘层**：只删除目标目录中 `v1-*.json` 文件；同目录的其它文件不会被缓存读取或清理。
- `novel-cli clean cache` 清理的是配置的缓存目录（站点 Cookie、章节缓存等），**不会**清空搜索缓存。

### 用 `doctor` 诊断

`novel-cli doctor` 的 `search_cache` 项是只读快照：只统计，不清理、不打开 payload，报告里不出现关键词、站点选择或过滤条件。

```bash
# 只看搜索缓存这一项；没有 jq 时可在整份 JSON 的 checks[] 里找 "key": "search_cache"
novel-cli doctor --json | jq '.checks[] | select(.key == "search_cache")'
```

字段含义（`memory_entries`、`expired_entries`、`disk_enabled`、`disk_entries`、`hits`、`misses`、`evictions`、`fingerprint`）与读法见 [CLI 用法 § doctor](./cli-examples.md#doctor-subcommand) 的「搜索缓存诊断」。要点：

- `hits` / `misses` / `evictions` 是**当前进程**的累计值。`doctor` 是新起的进程，通常全为 `0`，这不代表缓存故障。
- `disk_enabled=false`、`disk_entries=0` 是默认的仅内存模式，不是故障。
- `fingerprint` 变化说明搜索器集合或浏览器辅助站点集合变了，旧的聚合条目会全部失效。

## 失败、退出码与 JSON {#failures}

### 单站点失败不影响整体

- 每个站点有独立的墙钟预算（`--timeout`，默认 5 秒）。超时站点会被取消并计为一次 `failed`，其它站点的结果照常返回。
- 站点抛异常、返回的不是列表等，也只记为该站点失败，不会让整次聚合搜索崩掉。
- 聚合搜索（不写 `--site`）会跳过配置为「浏览器辅助」的站点，事件类型为 `browser_skipped`，这**不是失败**；显式 `--site <该站点>` 才会启用其浏览器回退。
- `nsfw` 不匹配的站点在聚合搜索里会被静默跳过。
- 小说搜索**没有跨调用的失败熔断**：不像音乐聚合搜索那样把失败平台冻结 10 分钟，每次搜索都会重新尝试每个被选中的站点。所谓「熔断」只发生在单次调用内部：到点即取消，不再等待。

### CLI 退出码

人类可读模式下，CLI 会在 stderr 打印每个站点的事件，最后一行是汇总：

```text
✓ qidian · 8 result(s)
✗ biquge5 · Search failed: ...
↷ fanqienovel · skipped (browser-assisted)
3 site(s) completed / 1 failed / 0 skipped
```

| 情形 | 退出码 | 说明 |
| --- | --- | --- |
| 搜索完成（≥1 个站点作答，包括 0 条结果） | `0` | 正常 |
| 部分站点失败/超时，但仍有站点作答 | `0` | 结果里只含成功站点的行；汇总行会显示失败数 |
| **所有**作答站点都失败（0 个 `completed`，≥1 个 `failed`） | `1` | 视为故障，而不是「没有这本书」 |
| 显式 `--site` 拼错或插件未安装 | `2` | stderr 列出可用站点；不会输出空数组冒充成功 |
| 关键词为空；`--min-words > --max-words`；日期非法；`--timeout` 为 `nan`/`inf`；`--json` 与 `--first` 同用 | `2` | 用法错误 |
| 交互模式下用户取消选择 | `0` | 不下载 |
| 选定后登录、下载或导出失败 | `1` | 与搜索本身无关 |

若既没有 `completed` 也没有 `failed`（例如所选站点全部被跳过），按正常结束处理，退出码为 `0`。

`--limit` 或 `--site-limit` 小于 1 时会被静默提升为 1；有限的非正 `--timeout` 会被提升为 0.1 秒；`nan` / `inf` 则是用法错误。

### `--json` 的行为

- stdout 只输出**一行** JSON 数组（`ensure_ascii=False`，紧凑分隔符）；每个站点的事件与汇总行都走 stderr，stdout 保持纯净。
- 数组元素是站点原始字段加上三个派生字段：

  ```json
  {
    "site": "qidian",
    "book_id": "123456",
    "book_url": "https://...",
    "cover_url": "https://...",
    "title": "斗破苍穹",
    "author": "天蚕土豆",
    "latest_chapter": "第 1 章",
    "update_date": "2024-01-01",
    "word_count": "100万字",
    "priority": 1,
    "rank_score": 0.912345,
    "match_tier": 4,
    "query_intent": "title"
  }
  ```

- `--group` 时每行额外带 `sources`（全部命中站点，最佳来源在前），`site` / `book_id` / `book_url` 指向最佳来源。
- **即使所有站点都失败，JSON 也会先输出**（通常是 `[]`），随后进程以退出码 `1` 结束。脚本应同时检查退出码，不能只看数组是否为空。
- 0 条结果且至少一个站点作答时，仍退出 `0`；stderr 会给出 `No results found for '<keyword>'.`，便于和故障区分。

REST 端点的形状不同：`POST /search` 返回 `{total, results, query_intent}`（派生字段在行内），站点全部失败时仍是 `200` 与 `total: 0`；未知站点是 `422`；请求超过服务端总预算返回 `504`。

## 常见问题 {#faq}

### 结果很少或为空

1. 看汇总行：`N completed / M failed / K skipped`。若 `failed` 很多，多半是所有站点都在 5 秒预算内没答完；提高 `--timeout` 或先用 `--site` 锁定一个站点验证。
2. 若 `completed` 很多但结果为空，检查关键词是否过于具体，或换用「书名 + 作者」的多词写法。
3. 聚合搜索会跳过浏览器辅助站点（如番茄）；需要它们时显式 `--site fanqienovel`。
4. 设置过 `--min-words` / `--updated-after` 时，缺少对应字段的行会被丢弃；先去掉过滤确认书本身能搜到。
5. `--site` 写错会以退出码 `2` 报错，并列出可用站点，而不是返回空列表。

### 排序看起来不对

- `quality` 是**综合分**，不是纯相关度：相关度占 0.55，字数、更新时间、站点优先级与完整度合计占 0.45。看 `--json` 里的 `rank_score` 与 `match_tier` 可以解释每一行的位置。
- 判定出查询意图时，外层键是主字段的 `match_tier`。一本元数据稀疏但书名精确匹配的书，会故意排在「书名恰好包含作者名」的富元数据书前面。
- `rank_score` 含更新时间信号，跨调用可能有极小漂移；`match_tier` 不会。
- 明确按某个字段排时，直接换键：`--sort title` / `author` / `words` / `update`。注意 `words` / `update` 缺失值按 -1 处理，默认降序下排在最后。
- 主键相同的行按内容元组（站点、书名、`book_id`……）稳定排序，和站点返回顺序无关；看起来「没变」通常是因为这些字段也相同。

### 缓存似乎没有生效

- 普通 `novel-cli` 调用是独立进程，内存缓存随进程结束消失；跨进程复用需要磁盘层，且环境变量必须在进程启动前设置。
- TTL 默认 300 秒；超过后重复搜索会重新访问站点。
- 检查 key 是否真的相同：`--site` 集合（顺序无关，但多一个/少一个都不同）、`--site-limit`、`--timeout`、`nsfw`、过滤条件、聚合配置指纹都会参与 key。
- `--sort`、`--order`、`--limit`、`--group` **不**参与 key；只改这些仍应命中。
- 空结果不缓存；条目数超过 64 会 LRU 淘汰。
- 用 `doctor --json` 看 `hits` / `misses` / `evictions` / `fingerprint`，但注意这些计数属于运行 `doctor` 的那个进程。

### 多词查询会让结果变少吗

不会因为「拆分」本身变少。多词评分只会抬高相关度，不改变站点返回的行集；可能变化的是排序（意图可能退为「无明确意图」，不再按主字段层级排序）以及相关度下限保留哪些行。
